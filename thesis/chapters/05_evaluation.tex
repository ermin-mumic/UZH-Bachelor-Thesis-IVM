\chapter{Evaluation}
\label{ch:evaluation}

This chapter evaluates the decomposition of Chapter~\ref{ch:ivm}, realised as the SQL pipelines of Chapter~\ref{ch:implementation}, against a flat-join baseline.
The baseline is the flat join query, which Feldera maintains incrementally just as it does the decomposition's views.
The engine and the data are held fixed, so what we isolate is the effect of the rewrite alone: whether maintaining the query as its decomposition's views is cheaper, in throughput and peak memory, than maintaining it as one flat view. The variants that materialise the full output all return the same result, which doubles as a correctness check (Section~\ref{sec:methodology}).

The reported metrics and the pipeline notation are defined in full here, expanding the brief description given with the harness (Section~\ref{sec:harness}). The experimental setup, datasets, hypotheses, and results then follow in turn.

\section{Experimental Setup}
\label{sec:setup}

All experiments were run on \texttt{dast-cpu05}, a CPU-only node of the DaST research cluster at the Department of Informatics (IfI), University of Zurich.

The node has two Intel Xeon Silver 4214 processors at $2.20$\,GHz ($12$ cores each, for $24$ physical cores and $48$ hardware threads), $196$\,GB of main memory and a local SSD. Datasets reside on the node's local scratch storage ($492$\,GB) and are read locally, so that data access introduces no network overhead. The host runs Debian GNU/Linux 12 (bookworm) with Linux kernel \texttt{6.1.0-45-amd64}.

The Feldera engine was deployed on the same host from the official \texttt{pipeline-manager} Docker image in its default configuration, with no changes to the engine itself other than the volume mounts described in Section~\ref{sec:harness}: the container's storage directory is bind-mounted to host scratch to hold the large intermediate views, and the dataset directory is mounted read-only into the container. We pin Feldera to version $0.286.0$ in both \texttt{docker-compose.yaml} (the engine image) and \texttt{requirements.txt} (the Python client), so that the engine and the harness driving it move together. The host ran Docker Engine $29.7.0$ and Python $3.11$. The harness runs directly on the host and drives the containerised engine through its REST API. Every variant begins from a cold start, with the engine's storage wiped between variants (Section~\ref{sec:harness}), so that no residual state or cache from an earlier run can influence a measurement.

The datasets were streamed from local CSV files into Feldera through the \texttt{file\_input} connectors described in Section~\ref{sec:pipeline}, simulating a high-velocity, insert-only ingestion.

\section{Metrics and Pipelines}
\label{sec:methodology}

\subsection{Metrics}

As described in Section~\ref{sec:harness}, the harness samples the running pipeline every five seconds, and once more when it finishes, recording at each sample its uptime, the number of input records processed so far, and its resident-set size (RSS).
Every figure we report is derived from this polling.
From a finished run we take three metrics: the \emph{time}, the wall-clock duration until the pipeline has ingested the whole dataset and its views are up to date, the \emph{throughput}, the number of input records processed per second, computed as the total records over that uptime, and the \emph{peak memory}, the largest RSS seen across all samples of the run.
Alongside these we report the size of the materialised \texttt{RESULT} view, in rows, and the \emph{speedup}, the ratio of the baseline's time to the variant's time, which expresses how many times faster (or, when below one, slower) a variant maintains the query than the flat baseline.

Every experiment is run as three independent trials, with the engine's storage cleared between them so that each trial starts from a clean state.
We report the time and throughput as the mean over the three trials, and the peak memory as the maximum over them, so that the memory figure reflects the worst case a run reached rather than a smoothed average.
An entry marked \texttt{TO} denotes an experiment in which all three trials hit the three-hour timeout without finishing.
For such an experiment we still report the peak memory the engine reached and, in parentheses, the mean fraction of the input processed when the timeout struck, but not its output size, throughput, or speedup, since the run never completed. A run that instead crashes after exhausting the storage volume is marked \texttt{OOS} and reported the same way.
The baseline is the reference for the speedup and so is always $1.00\times$. When the baseline itself times out, its true time exceeds the three-hour timeout, so a variant that finished is reported with a lower-bound speedup $>\!N\times$, where $N$ is the timeout divided by the variant's time.
Table~\ref{tab:metrics} summarises the metrics and how each is aggregated.

\medskip
\label{sec:caveats}
A few measurement artefacts should be kept in mind when reading the tables:
\begin{itemize}
    \item \textbf{Averaging noise.} The reported times are the mean of three trials, so differences on the order of $0.05$\,min lie within trial-to-trial variance and should not be over-interpreted.
    \item \textbf{Memory sampling.} Peak memory is sampled every five seconds, so for a very short run (for example $0.10$\,min) the reported value may reflect a single, possibly unrepresentative, snapshot rather than the true peak.
\end{itemize}

\subsection{Pipelines and Variants}
\label{sec:variants}

Every query is run as a flat baseline and as a family of decomposition variants. In the result tables (Tables~\ref{tab:results_soc-Epinions1}--\ref{tab:results_imdb_job}) each decomposition variant is named by a compact symbol recording three choices: how the decomposition tree is rooted, whether it uses the standard IVM$^+$ decomposition or our variant, and how much of the result the pipeline reconstructs.

\begin{itemize}
    \item \textbf{Baseline}: the query as a single flat join, with no decomposition. This is the reference against which the decomposition variants are compared.
    \item \textbf{Orientation ($D_1$, $D_2$)}: the bag relations and their $P'$-semijoin filters are defined over a \emph{rooted} tree decomposition (Section~\ref{sec:bag_relations}), but the decomposition itself does not fix the root. Re-rooting changes which bag is a parent of which, and so the direction in which the $P'$-relations filter and the order in which the bags are maintained. $D_1$ and $D_2$ denote two orientations of the same decomposition: $D_1$ is the less balanced one, a deeper, more chain-like tree with the larger relations in the lower bags, and $D_2$ is the more balanced one, with the bags spread across independent branches and the larger relations nearer the root. Where a decomposition admits only one meaningful orientation, for example a two-bag one, we report only $D_1$.
    \item \textbf{IVM$^+$ ($D$) or the variant ($D'$)}: the unprimed $D$ builds each bag query the standard IVM$^+$ way, keeping every atom that shares a variable with the bag and projecting the partially overlapping ones onto the bag's variables as semijoin filters (Section~\ref{sec:ivm_algorithm}). The primed $D'$ is our variant, which drops those projected atoms and keeps only the atoms fully contained in the bag (Section~\ref{sec:variant_no_semijoin}). The two give the same result and differ only in intermediate size and join work.
    \item \textbf{Reconstruction ($D^{\text{full}}$, $D$, $D^{\text{count}}$)}: $D^{\text{full}}$ performs the reconstruction join over all the bags to materialise the complete result (Section~\ref{sec:bag_relations}). The plain $D$, shown indented beneath its $D^{\text{full}}$, stops at the root bag and skips the reconstruction, maintaining only the bag hierarchy. $D^{\text{count}}$ returns the size of the full result through the semiring extension, without ever materialising the output (Section~\ref{sec:semiring}).
\end{itemize}

After every trial the harness verifies the run by reading the row count of the maintained output view (Section~\ref{sec:harness}). For the baseline and the full-reconstruction variants this is the size of the complete result, which they must all agree on. The without-reconstruction variants materialise only the root bag, so their reported count is that bag's size rather than the full result, and the count variant is checked against the full result size, which it must reproduce through the semiring extension without materialising the output.

Because the baseline maintains the full join result as a single materialised view, a like-for-like comparison must ask the decomposition to produce that same output. The full-reconstruction variant ($D^{\text{full}}$) does so, re-joining the bags into the complete result, so it and the baseline maintain the same answer and differ only in how they compute it. The without-reconstruction variant ($D$) instead stops at the root bag and never forms the full output. This is closer to how incremental maintenance is normally used, keeping a compact structure the result can be read from on demand rather than the result itself (Chapter~\ref{ch:introduction}), so it is not a like-for-like competitor to the baseline but a measure of how cheaply the decomposition alone can be maintained. The count variant ($D^{\text{count}}$) lies between the two, reporting the result's size without materialising it.

\medskip
All experiments were run as pipelines in which every table and every view is materialised, so that any of them can be queried directly. In practice this is often unnecessary, so it is a conservative choice, and one that weighs more heavily on the decomposition, which introduces many additional views. As described in Section~\ref{sec:feldera}, materialising a table or view can slow a pipeline down, so any advantage the decomposition shows here is obtained despite this. To gauge the effect, we ran a subset of the experiments in which only each pipeline's terminal view is materialised (Section~\ref{sec:pipeline}). Tables with a primary key stay materialised regardless, since Feldera maintains those automatically (Section~\ref{sec:feldera}). These runs are reported separately, one table per dataset, in Appendix~\ref{app:results_ablation}.

\subsection{Graph datasets}
The graph datasets are three directed graphs from the SNAP collection~\cite{snapnets}, each stored as a single \texttt{EDGES} relation. \texttt{soc-Epinions1} is a who-trusts-whom social network ($|V| = 75'879$, $|E| = 508'837$), \texttt{cit-HepTh} an arXiv high-energy-physics citation network ($|V| = 27'770$, $|E| = 352'807$), and \texttt{p2p-Gnutella31} a Gnutella peer-to-peer snapshot ($|V| = 62'586$, $|E| = 147'892$). Every query is a self-join over the edge relation: one acyclic query and several cyclic queries (Table~\ref{tab:queries_graph}).

Because every atom is the same \texttt{EDGES} relation, the projections that separate IVM$^+$ from the variant only filter a bag down to the nodes with an edge on one endpoint, almost every node in a dense graph, and so barely filter while still costing extra work. We therefore run only the variant on these datasets ($D'$).

Each query is run under two input configurations. In the first, the edge file is ingested through a single connector into one \texttt{EDGES} table, which the query aliases once per atom. In the second, each atom has its own table, all loaded with the same edge file, so the query remains a self-join but over separate copies of the data. Both configurations produce the same result and are reported separately, labelled by the number of connectors. \section{Hypotheses}
\label{sec:hypotheses}

Recall the question: is a query cheaper to maintain as its decomposition's views than as one flat baseline view? The $O(N^{w(Q)})$ bound of Section~\ref{sec:fhw} assumes each bag is evaluated with a worst-case-optimal join. Feldera does not implement worst-case-optimal joins~\cite{budiu2023DBSP}, so we do not claim to obtain that bound, and whether the decomposition nonetheless outperforms the flat baseline is what the following hypotheses test. The first two concern query structure (\hyperlink{h1}{H1}, \hyperlink{h2}{H2}). The next four concern how cheaply the decomposition itself runs: its reconstruction and without-reconstruction, IVM$^+$ and variant, semiring extension, and orientation choices (\hyperlink{h3}{H3}--\hyperlink{h6}{H6}). Two setup choices, the input configuration (Section~\ref{sec:datasets}) and how much of each pipeline is materialised (Section~\ref{sec:variants}), are controls on the fairness of the comparison rather than claims about the approach, and we return to them with the results.

\begin{description}
    \item[\hypertarget{h1}{H1 (Acyclic queries).}] As established in Section~\ref{sec:fhw}, an acyclic query has $w(Q) = 1$: a minimum fractional hypertree width decomposition can give each atom its own bag, so no bag joins more than one full relation. As shown in Chapter~\ref{ch:ivm}, that relation is still combined with the $P'$-views of the bag's children (Section~\ref{sec:pipeline}) and, under IVM$^+$, with the projected atoms the bag carries (Section~\ref{sec:ivm_algorithm}). These only filter tuples from the relation, making it smaller, rather than adding another full relation to the join.

    The reconstruction therefore performs the same join as the baseline, but over relations the filters have already reduced, and we accordingly expect the decomposition to be faster than the flat baseline on acyclic queries. Maintaining these views is itself an overhead, though. The decomposition turns each bag into a $Q'$-view and each non-root bag into a further $P'$-view, and each keeps the state needed to maintain it even when not materialised (Section~\ref{sec:feldera}), so we also expect the decomposition to reach a higher peak memory than the baseline, growing with the number of bags. How much the reconstruction itself costs (\hyperlink{h3}{H3}), how IVM$^+$ compares with its variant (\hyperlink{h4}{H4}), and the semiring extension (\hyperlink{h5}{H5}) are examined separately.

    \item[\hypertarget{h2}{H2 (Cyclic queries).}] A cyclic query has $w(Q) > 1$, so a minimum fractional hypertree width decomposition must place several atoms in at least one bag (Section~\ref{sec:fhw}). Such a bag joins those atoms into a closed sub-pattern and passes up a $P'$-view carrying a joint constraint over several of them, rather than the single-atom projection an acyclic bag would pass. The bags' $Q'$-views then enter the reconstruction already filtered and already closed, unlike the baseline, which joins the raw relations directly and may build large intermediates unless Feldera's optimiser finds a comparably good plan on its own.

    We therefore expect the decomposition to run faster than the baseline on cyclic queries, an advantage that comes from these joint-constraint filters and pre-closed sub-patterns, and that should widen with data density and query size.

    As in \hyperlink{h1}{H1}, the decomposition maintains a $Q'$-view per bag and a $P'$-view per non-root bag, each keeping the state needed to maintain it even when not materialised (Section~\ref{sec:feldera}), so we again expect a higher peak memory, growing with the number of bags and the size of the multi-relation joins they hold.

    \item[\hypertarget{h3}{H3 (Reconstruction).}] Every variant has a terminal view. The full-recon\-struc\-tion variant ($D^{\text{full}}$) ends in the \texttt{RESULT} view, the reconstruction join of all the bags' $Q'$-views into the complete output (Section~\ref{sec:pipeline}). The without-reconstruction variant ($D$) instead takes the root bag's $Q'$-view as its terminal, so it maintains only the bag hierarchy and never forms the full result. It is therefore not a like-for-like alternative to the baseline (Section~\ref{sec:variants}), but comparing it with $D^{\text{full}}$ isolates the cost of the reconstruction itself.

    The two maintain the same bag views and differ only in the reconstruction. That step is itself an incrementally maintained join, updated on every insertion. It joins all the bags' $Q'$-views and holds the full output it produces, whereas $D$ stops at the root bag. Because every update that reaches a bag must be propagated through this extra join, and because the full output it stores can be far larger than any single bag, we expect the reconstruction to be a substantial part of the decomposition's cost in both time and peak memory. The without-reconstruction variant should accordingly be cheaper than the full one, by a margin that grows with the size of the output it avoids. As this concerns the reconstruction step rather than the query's structure, we expect it to hold for both acyclic and cyclic queries.

    \item[\hypertarget{h4}{H4 (IVM$^+$ versus the variant).}] IVM$^+$ ($D$) and the variant ($D'$) differ only in each bag's underlying $Q$-relation (Section~\ref{sec:variant_no_semijoin}): IVM$^+$ keeps the partially overlapping atoms as projected semijoin filters, whereas the variant keeps only the atoms fully contained in the bag. The $Q'$- and $P'$-views are built the same way on top of it.

    A projected atom either removes tuples the child $P'$-views would not, or merely repeats filtering they already do. Where it genuinely filters, IVM$^+$'s bag $Q'$-views hold fewer tuples than the variant's, so we expect IVM$^+$ to reach a lower peak memory and, with smaller $Q'$-views to join, a faster reconstruction. Where the projection is redundant it only adds upkeep, so there we expect the variant to be cheaper. As the two differ in this one definition alone, we expect a modest gap either way, and which side wins is the empirical question Chapter~\ref{ch:ivm} leaves open. We evaluate this comparison on the relational datasets only, since on the graph datasets we maintain just the variant, for the reason given with those datasets (Section~\ref{sec:datasets}).

    \item[\hypertarget{h5}{H5 (Semiring extension).}] The count variant ($D^{\text{count}}$) reports the size of the full result through the semiring extension (Section~\ref{sec:semiring}), without ever materialising it. It maintains the same bag hierarchy as the without-reconstruction variant ($D$), with each $P'$-view now carrying a count beside its bridge variables (Section~\ref{sec:pipeline}).

    Like $D$, it never performs the reconstruction join over all the bags' $Q'$-views, which \hyperlink{h3}{H3} expects to be the heavy part of the pipeline. On top of the bag hierarchy it adds only the annotation carried up the tree and the final scalar aggregation. We therefore expect $D^{\text{count}}$ to run nearly as cheaply as $D$ and far below the full reconstruction $D^{\text{full}}$, at a peak memory comparable to $D$, perhaps slightly higher from the annotations it maintains. It does this while still returning a summary of the full result that $D$, stopping at the root bag, does not. Because this again concerns the reconstruction rather than the query's structure, we expect it to hold for both acyclic and cyclic queries.

    \item[\hypertarget{h6}{H6 (Orientation).}] A tree decomposition fixes the bags but not the root (Section~\ref{sec:bag_relations}). Where a decomposition admits more than one orientation, we evaluate two per query: $D_1$, a deep, chain-like tree with the larger relations in the lower bags, and $D_2$, a balanced one with them nearer the root (Section~\ref{sec:variants}). A two-bag decomposition admits only one meaningful orientation, reported as $D_1$.

    Since a bag's $Q'$-view is filtered by its children's $P'$-views, a large relation placed near the root is reduced by the smaller relations beneath it before it reaches the reconstruction, while one placed low stays barely filtered. We therefore expect the balanced $D_2$, keeping the larger relations near the root, to feed the reconstruction smaller $Q'$-views than the chain-like $D_1$, which rejoins its large, barely filtered relations. Its balanced shape may also let independent branches be maintained in parallel rather than along one long chain. On both counts we expect $D_2$ to reach a lower peak memory and run faster.

    We are least confident in this prediction of the six: it rests on the $P'$-views being selective, and where they remove few tuples the orientation should barely matter.
\end{description}

\section{Results and Discussion}
\label{sec:results_discussion}

We discuss the results hypothesis by hypothesis, drawing on the main experiment tables in Appendix~\ref{app:results_main} (Tables~\ref{tab:results_soc-Epinions1}--\ref{tab:results_imdb_job}), in which every table and view is materialised. Every variant that materialises the full result agrees on the output count (Section~\ref{sec:harness}), which we take as confirming they compute the same result. After the six hypotheses we return to the two setup controls, the input configuration and how much of each pipeline is materialised, the latter drawing on the terminal-only ablation of Appendix~\ref{app:results_ablation} (Tables~\ref{tab:results_ablation_soc-Epinions1}--\ref{tab:results_ablation_imdb_job}).

\subsection{H1: Acyclic Queries}
\label{sec:disc_h1}

H1 predicted the decomposition would be faster than the baseline on acyclic queries and would pay for it in peak memory. The throughput prediction is not borne out. On the TPC-H 4 Table Path Query and 5 Table Path Query, whose output is exactly the size of the driving \texttt{LINEITEM} relation and where the baseline finishes, neither the full reconstruction $D^{\text{full}}$ nor its variant $D'^{\text{full}}$ is ever faster than the baseline: both match it at scale factor~1 and fall away as the data grows, to between $0.61$ and $0.62\times$ for $D_1^{\text{full}}$ and between $0.72$ and $0.74\times$ for $D_1'^{\text{full}}$ at scale factor~30, on both paths. The memory prediction, by contrast, holds: both exceed the baseline's peak memory everywhere, $D^{\text{full}}$ by up to $2.6\times$ (for example $42.2$ against $16.2$\,GiB on the 4 Table Path Query at scale factor~10) and the variant by somewhat less, and the gap widens with both the scale factor and the number of tables, that is the number of bags.

This follows from the schema topology of these two queries. Each is a chain of foreign-key to primary-key joins, and referential integrity together with the uniqueness of the primary keys means every child tuple matches exactly one parent, one line item with its order, that order with its customer, and so on. These joins only enrich tuples with further columns, without filtering or multiplying them, so the result is exactly the size of \texttt{LINEITEM}. The $P'$-views and projected atoms therefore have nothing to remove, since with no dangling tuples their semijoins filter nothing (Chapter~\ref{ch:ivm}). The reconstruction then reproduces the same enrichment as the baseline over relations it has not shrunk, so it does the baseline's work plus the upkeep of the extra bag views. That upkeep is what the memory figures show, and because it scales with the data while the baseline stays a single lean join, the slowdown grows with the scale factor. Since the projected atoms filter nothing here, dropping them makes the variant the cheaper of the two, which we take up under \hyperlink{h4}{H4}.

The IMDB queries behave differently. Acyclic Query 1, a five-table path, shows no difference from the baseline ($1.00\times$), but Acyclic Query 2, a ten-table tree, is the one acyclic query where the decomposition is faster, in both orientations and for both IVM$^+$ and the variant, from $1.28\times$ to $1.52\times$, at essentially the baseline's peak memory (which orientation does better is taken up under \hyperlink{h6}{H6}). Unlike the synthetic TPC-H chains, the real, correlated JOB data does contain dangling tuples, which the decomposition appears to remove early rather than carrying them through a long flat join, an effect we infer from the speedup since we do not measure intermediate sizes directly.

Finally, the TPC-H 3 Table Path Query and the 5 Path Query on the two dense graphs have enormous outputs, up to tens of trillions of rows, and here both the baseline and the full reconstruction time out, so neither produces the full result and only the variants that avoid materialising it finish. That is a property of the reconstruction rather than of the acyclic structure, and we return to it under \hyperlink{h3}{H3}.

\subsection{H2: Cyclic Queries}
\label{sec:disc_h2}

H2 predicted the decomposition would be faster than the baseline on cyclic queries, by a margin widening with data density and query size. On the dense graphs this is borne out. The clearest case is Cyclic Query~2 on \texttt{cit-HepTh}, where the baseline takes $80.77$\,min and the full reconstruction maintains the same $266$-million-row result in under two minutes, a $42.96\times$ speedup for $D_1'^{\text{full}}$ and $52.11\times$ for $D_2'^{\text{full}}$. Where the baseline times out altogether, the full reconstruction in either orientation still finishes and beats it, by lower bounds from $>7\times$ on Cyclic Query~4 to $>191\times$ on Cyclic Query~1. Our running example, the diamond $Q_\diamond$ (Cyclic Query~3, Section~\ref{sec:queries}), is faster on both dense graphs, $5.64\times$ on \texttt{soc-Epinions1} and $6.68\times$ on \texttt{cit-HepTh}. Where the baseline also finishes, this speed does not cost memory, unlike the acyclic case: on \texttt{cit-HepTh} Cyclic Query~2 the decomposition's peak memory is $10$--$16$\,GiB against the baseline's $16$, and on the diamond $3.6$ against $7.5$\,GiB, since here it is avoiding a blow-up rather than duplicating a cheap join.

Two kinds of cyclic query on the graphs do not follow this pattern. The first is the four-cycle (Cyclic Query~6), the simplest of them. The baseline maintains it in well under a minute on both dense graphs ($0.19$\,min on \texttt{cit-HepTh}), and the full reconstruction is then slower rather than faster, $0.51\times$ on \texttt{soc-Epinions1} and $0.70\times$ on \texttt{cit-HepTh}, since there is no blow-up for the decomposition to avoid and only its extra views to maintain. The second is the sparse graph \texttt{p2p-Gnutella31}, which has so few cycles that its queries return at most sixteen thousand rows, and as few as none. The baseline handles every one in well under a minute, so with no blow-up to avoid the decomposition cannot win: it merely matches the baseline on the near-empty queries and falls behind where its bags still materialise many partial matches that never close into the small result, as on Cyclic Query~4 ($0.31\times$, at $10.7$ against $2.4$\,GiB).

On the denser \texttt{soc-Epinions1}, the same cyclic queries have far larger outputs, up to $234$ billion rows for Cyclic Query~2, and here even the full reconstruction times out alongside the baseline, since materialising a result of that size is infeasible. The flat plan's blow-up is still evident, the baseline timing out at $0.21\%$ of the input processed, and the variants that maintain the bag hierarchy without reforming the full result do finish where it and the reconstruction cannot. How cheaply that bag hierarchy alone runs, and why the reconstruction is the step that fails here, is taken up under \hyperlink{h3}{H3}.

The relational datasets reverse the graph picture. On TPC-H Cyclic Query~7, a four-cycle over four tables, the baseline maintains the query comfortably at every scale, from $1.02$ to $30.29$\,min, whereas the decomposition is slower at scale factor~1, $0.71\times$ for $D_1^{\text{full}}$ and $0.08\times$ for the variant $D_1'^{\text{full}}$, and by scale factor~10 these full reconstructions no longer finish at all, running out of storage or timing out. This is consistent with the mechanism behind the graph wins, now working against the decomposition rather than for it. On these key-based tables the flat join never blows up, its foreign-key to primary-key joins keeping the intermediates small, so the decomposition's bags have no blow-up to bound and only add the state their own two-table joins must maintain, which Feldera keeps whether or not the views are materialised (Section~\ref{sec:feldera}). The overhead is thus structural, not a matter of materialising the extra views. The variant fares far worse than IVM$^+$, $0.08\times$ against $0.71\times$, because it drops the semijoins that would shrink those bags, a gap we take up under \hyperlink{h4}{H4}.

IMDB Cyclic Query~8, a three-cycle over three tables of real data, is less clear-cut and hinges on the orientation. Rooted one way ($D_1$) the full reconstruction times out at $63\%$ of the input, rooted the other ($D_2$) it finishes, and in its best form $D_2'^{\text{full}}$ it is modestly faster than the baseline, at $1.34\times$. That the decomposition is competitive here at all, unlike on TPC-H, fits the correlated IMDB data giving its filters something to remove, as on the acyclic queries. The orientation dependence itself is taken up under \hyperlink{h6}{H6}.

Across the datasets, then, H2 holds in a sharpened form. The decomposition is faster than the baseline exactly where the flat plan blows up, on the dense graphs with genuinely large cyclic output, and the advantage grows with density and cycle size, reaching $42.96\times$ on \texttt{cit-HepTh} Cyclic Query~2. Where it wins it does so without the memory penalty of the acyclic case, its peak memory comparable to or below the baseline's, because the blow-up it avoids weighs more heavily on memory than the extra bag views it maintains. Every boundary confirms the same mechanism from the other side: on the sparse graph, the easy four-cycle (Cyclic Query~6), and the key-based TPC-H tables the baseline does not blow up, so the decomposition's bags have nothing to bound and only add their own state, and there the memory turns into an overhead again. The benefit is therefore specific to cyclic queries over dense data, not to cyclic structure alone. We read this from the run times and peak memory, in particular the baselines that time out early, rather than from intermediate sizes, which we do not measure directly.

\subsection{H3: Reconstruction}
\label{sec:disc_h3}

H3 predicted that the reconstruction is a substantial part of the decomposition's cost, so the without-reconstruction variant should be markedly cheaper than the full reconstruction, by a margin growing with the output it avoids. The results confirm this wherever both finish. On \texttt{cit-HepTh} Cyclic Query~2, dropping the reconstruction cuts the time from $1.88$ to $0.44$\,min and the peak memory from $16.1$ to $6.8$\,GiB ($D_1'^{\text{full}}$ against $D_1'$), as it stops at the $1.1$-million-row root bag rather than reforming the $266$-million-row result. The TPC-H 5 Table Path Query makes the point more sharply still. At scale factor~30 its root bag already equals the full output, both $180$ million rows, since the reconstruction only enriches each line item with further columns rather than adding tuples (\hyperlink{h1}{H1}). Yet the without-reconstruction $D_1$ is still faster and lighter than the full reconstruction $D_1^{\text{full}}$, $33.26$ against $62.56$\,min and $29.2$ against $51.2$\,GiB. The cost is thus the reconstruction join and the \texttt{RESULT} view it maintains, not merely the size of the result.

In the most pronounced cases the full reconstruction no longer completes at all, while the without-reconstruction variant still finishes. On the TPC-H 3 Table Path Query, whose full result reaches $36$ billion rows at scale factor~1, $D_1^{\text{full}}$ times out at every scale, whereas $D_1$, stopping at a root bag of only ten thousand rows, finishes in $1.02$\,min. The same pattern appears wherever the reconstructed output reaches into the millions or billions: on \texttt{soc-Epinions1} Cyclic Query~2 the full result is $234$ billion rows and $D_1'^{\text{full}}$ times out, while $D_1'$ finishes in $1.41$\,min, and on IMDB Cyclic Query~8 $D_1^{\text{full}}$ times out at $63\%$ of the input processed where $D_1$ finishes in $1.11$\,min. Here the reconstruction is not merely the larger part of the cost but the part that decides whether the query completes at all.

At the other end, where the full result is small or the whole run is brief, the reconstruction is negligible and the two variants coincide. On IMDB Acyclic Query~1 the full reconstruction and the without-reconstruction variant take the same $0.18$\,min, since the entire run lasts only seconds and reforming the $702$-thousand-row result costs nothing measurable. The \texttt{p2p-Gnutella31} queries whose results are near-empty behave the same way, with $D'^{\text{full}}$ and $D'$ within noise of each other. Across all of this the effect is the same for acyclic and cyclic queries alike, as H3 anticipated: it concerns the reconstruction step, not the shape of the query.

\subsection{H4: IVM\texorpdfstring{$^+$}{+} versus the Variant}
\label{sec:disc_h4}

H4 predicted no uniform winner between IVM$^+$ and the variant, with the variant cheaper where the projected atoms are redundant and IVM$^+$ cheaper where they filter. The results bear this out, and on most queries it is the variant that comes out ahead. Wherever the projected atoms filter little, the key-based TPC-H paths and the IMDB queries, dropping them leaves the variant as fast as IVM$^+$ or faster, and consistently lighter, because its bag views drop the projected-atom semijoins and so maintain less state. On the TPC-H 5 Table Path Query at scale factor~30 the variant $D_1'^{\text{full}}$ runs at $0.72\times$ against IVM$^+$'s $0.62\times$ and at $44.6$ against $51.2$\,GiB, and on the 4 Table Path Query at $0.74\times$ against $0.61\times$. On IMDB Acyclic Query~2 the variant is again the faster of the two, $1.52\times$ against $1.44\times$ and $14.4$ against $15.1$\,GiB. As Chapter~\ref{ch:ivm} anticipated, the projected atoms are largely redundant here: either they have little to remove, as on the zero-dangler TPC-H paths (\hyperlink{h1}{H1}), or the child $P'$-views already remove the same tuples. Either way, dropping them sheds their upkeep at no cost.

The exception is TPC-H Cyclic Query~7, the one query where IVM$^+$ clearly beats the variant. Here the semijoins genuinely filter, and dropping them lets the variant's bags grow far larger: at scale factor~1 $D_1'^{\text{full}}$ falls to $0.08\times$ against IVM$^+$'s $0.71\times$, and its peak memory rises to $31.4$ against $14.2$\,GiB, the one place the variant is the heavier of the two (both fail from scale factor~10 on). This is the case H4 set aside, a cyclic query whose projected atoms remove tuples the $P'$-views do not, so keeping them pays off. It does not generalise to every cyclic query, though: on IMDB Cyclic Query~8 the semijoins do not help, and the variant $D_2'^{\text{full}}$ ($1.34\times$) is faster than IVM$^+$ $D_2^{\text{full}}$ ($0.40\times$). Whether the projected atoms earn their keep is thus a property of the individual query, not of its being cyclic.

H4's prediction of no uniform winner holds, but the balance tips clearly toward the variant. On every query but TPC-H Cyclic Query~7 the variant is lighter than IVM$^+$ and no slower, bar a negligible margin on IMDB Acyclic Query~1, so as a default it is the better choice. On that one query IVM$^+$'s semijoins repay themselves, yet the gain is hollow: both variants stay far slower than the baseline there (\hyperlink{h2}{H2}), so IVM$^+$'s edge over the variant does not make the decomposition competitive. The variant's advantages, by contrast, appear on queries the decomposition actually wins, such as IMDB Acyclic Query~2 and Cyclic Query~8. The semijoins thus rarely earn their keep, and never turn a losing query into a winning one.

\subsection{H5: Semiring Extension}
\label{sec:disc_h5}

H5 predicted the count variant would run nearly as cheaply as the without-reconstruction variant and far below the full reconstruction, since it too skips the reconstruction join and only carries a count up the tree. This holds across the queries. On the diamond $Q_\diamond$ (Cyclic Query~3, Section~\ref{sec:queries}), the count finishes in $0.52$\,min on \texttt{soc-Epinions1} and $0.10$ on \texttt{cit-HepTh}, against $0.44$ and $0.10$ for the without-reconstruction variant and $0.74$ and $0.19$ for the full reconstruction. The same appears on \texttt{cit-HepTh} Cyclic Query~2, $0.52$\,min against $0.44$ and $1.88$, and on IMDB Acyclic Query~2, $1.19$ against $1.18$ and $2.02$. Its peak memory sits a little above the without-reconstruction variant's on most queries, from the counts it carries, and well below the full reconstruction's.

Where the full reconstruction cannot complete, the count still can, which shows the advantage of the semiring extension: it reports the size of a result too large to materialise. On IMDB Cyclic Query~8, \texttt{soc-Epinions1} Cyclic Query~2 and the TPC-H 3 Table Path Query at scale factor~1 the full reconstruction times out while the count finishes in one to two minutes, returning row counts of $1.9$ million, $234$ billion and $36$ billion without ever forming the result.

The count does not always stay this close to the without-reconstruction variant. On the largest cyclic queries, where the bags hold the most tuples to group, the per-bag grouping and counting that replaces the plain \texttt{SELECT DISTINCT} (Section~\ref{sec:pipeline}) adds noticeably to the cost. On \texttt{cit-HepTh} Cyclic Query~4 the count takes $15.12$\,min and $25.3$\,GiB, above the without-reconstruction variant's $6.03$\,min and $22.6$\,GiB but still well below the full reconstruction's $24.08$\,min and $36.6$\,GiB. On \texttt{soc-Epinions1} Cyclic Query~5 it takes $41.83$\,min against the without-reconstruction variant's $24.00$, where the full reconstruction times out altogether. The count is therefore still the cheaper way to obtain the result's size, in both time and memory, even on the queries where it costs most.

\subsection{H6: Orientation}
\label{sec:disc_h6}

H6 predicted the balanced orientation $D_2$ would outperform the chain-like $D_1$ where the $P'$-filters are selective, while flagging this as the least certain prediction. It is not borne out as a directional rule: neither orientation is uniformly better. The effect is sharpest without the reconstruction, where the bag hierarchy is the whole cost: $D_2$ leads $D_1$ by about two to one on \texttt{soc-Epinions1} Cyclic Query~5 ($11.20$ against $24.00$\,min, $16.0$ against $26.9$\,GiB) and on \texttt{cit-HepTh} Cyclic Queries~4 and 5 ($3.16$ against $6.03$ and $0.61$ against $1.16$\,min), yet $D_1$ wins by an even larger margin on \texttt{soc-Epinions1} Cyclic Query~2 ($1.41$ against $5.19$\,min). With full reconstruction the margins narrow, and the same split persists: $D_2$ ahead on \texttt{cit-HepTh} Cyclic Queries~2, 4 and 5, $D_1$ on Cyclic Query~1 and IMDB Acyclic Query~2. On two queries $D_2$ completes where $D_1$ times out, \texttt{soc-Epinions1} Cyclic Query~4 and IMDB Cyclic Query~8, its one consistent advantage.

The mixed outcome likely reflects a trade-off between two effects of re-rooting, though our measurements cannot confirm it. Re-rooting leaves the bags unchanged and alters only the direction in which the $P'$-filters flow. In the balanced $D_2$ the constraints from different parts of the query meet near the root over few steps, so where the filters are selective the heaviest bags are pruned early. In the chain $D_1$ the filters apply one after another, which instead helps when the bag at the base of the chain is already small on the given data, since the whole chain then stays thin. Which effect dominates depends on the data, not the query alone, which is why Cyclic Query~2 changes winner between \texttt{soc-Epinions1} and \texttt{cit-HepTh}. Because we observe only time and peak memory, and not the sizes of the intermediate bags, this remains a plausible reading rather than a demonstrated one.

The original rationale for H6, that a balanced tree keeps the larger relations near a filtered root, does not carry over to the graph queries, where every atom is the same \texttt{EDGES} relation and orientation is a matter of tree shape alone. What the results do establish is that orientation is a real and at times decisive factor, changing runtime by up to nearly a factor of four and, on two queries, deciding whether the query completes at all. Which orientation is preferable depends on the data as much as the query, however, and is not something our measurements let us predict in advance, so it is best treated as a choice to tune empirically rather than a fixed rule.

\subsection{Controls}
\label{sec:controls}

The remaining two settings are controls on the fairness of the comparison rather than tests of the approach. The first is the input configuration of the graph queries. Each is run both through a single connector, ingesting the edge file once into one \texttt{EDGES} table aliased per atom, and through one connector per atom, each re-ingesting the same file (Section~\ref{sec:datasets}). The two produce the same result in essentially the same time and at comparable memory. On \texttt{cit-HepTh} Cyclic Query~2 the full reconstruction $D_1'^{\text{full}}$ takes $1.88$\,min under either configuration, at $16.1$ and $16.4$\,GiB, and on the diamond $Q_\diamond$ (Cyclic Query~3) on \texttt{soc-Epinions1} it takes $0.74$\,min, at $9.7$ and $10.8$\,GiB. Their throughputs differ in proportion to the number of connectors, but only because each connector re-ingests the file and counts another pass, which is why we compare the configurations on time rather than throughput. Using many connectors adds a small ingestion overhead, as on \texttt{soc-Epinions1} Cyclic Query~1, where the without-reconstruction $D_1'$ takes $0.85$ against $1.11$\,min with nine connectors. That the two are otherwise indistinguishable confirms that the cost of these pipelines lies in maintaining the views, not in ingesting the data. A single connector is nonetheless the better choice in practice, since it reads the data once and avoids even this small overhead.

The second control is how much of each pipeline is materialised. Every result so far comes from pipelines in which every table and view is materialised, a conservative choice that weighs on the decomposition and its many additional views. Repeating a subset of the experiments with only each pipeline's terminal view materialised (Appendix~\ref{app:results_ablation}) leaves every finding of Sections~\ref{sec:disc_h1} to~\ref{sec:disc_h6} in place. The dense-graph wins persist: the full reconstruction $D_1'^{\text{full}}$ of the diamond $Q_\diamond$ (Cyclic Query~3) runs at $5.88\times$ on \texttt{soc-Epinions1} against $5.64\times$ in the main run, and of \texttt{cit-HepTh} Cyclic Query~2 at $41.76\times$ against $42.96\times$. The acyclic TPC-H paths still show no throughput gain, the full reconstruction $D_1^{\text{full}}$ remaining below the baseline, and the sparse and relational losses still lose, $D_1'^{\text{full}}$ on \texttt{p2p-Gnutella31} Cyclic Query~4 at $0.30\times$ against $0.31\times$.

Peak memory falls, by a few per cent on TPC-H and up to a quarter on some graph queries, but never enough to change a verdict. The full reconstruction $D_1^{\text{full}}$ of the TPC-H 4 Table Path Query at scale factor~30 drops from $47.2$ to $43.0$\,GiB, still far above the baseline's $24.3$. This saving is bounded, though: Feldera maintains each bag view's state whether or not it is materialised (Section~\ref{sec:feldera}), so removing the materialisation lightens the pipeline, in memory and often in time, without removing the decomposition's structural cost. TPC-H Cyclic Query~7 at scale factor~1 makes the point sharply, its full reconstruction moving only from $0.71\times$ to $0.72\times$ and from $14.2$ to $13.2$\,GiB, so its overhead is structural rather than an artefact of materialising the views. That every finding survives the ablation confirms the results are not an artefact of materialising every view. If anything, materialising more than the decomposition needs held it to a slightly harsher standard than a leaner deployment would.
